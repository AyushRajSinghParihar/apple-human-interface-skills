# Virtual keyboard visual examples

Source: [Apple HIG Virtual keyboards](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards). Snapshot: 2026-10-25.

These original notes describe the inspected primary and alternate-appearance examples. They explain the depicted entry choices; use system keyboard and content types so actual keys can adapt to language, locale, and device.

| Illustrated type | Visible distinction and selection lesson |
| --- | --- |
| ASCII-capable | A letter keyboard with a numbers switch, space, Return, and prediction row; useful when the input needs ASCII-capable entry. |
| ASCII-capable number pad | A large digit grid with deletion; unlike a general letter keyboard, its immediate surface is numerical. |
| Decimal pad | Adds a decimal separator to the numerical surface for fractional amounts. |
| Default | General letter entry with language/emoji access and standard word predictions. |
| Email address | Gives direct access to `@` and period beside the space bar. |
| Name/phone | Begins with letters and offers a numerical mode for combined name/phone entry. |
| Number pad | Presents digits directly, avoiding a switch through the alphabetic keyboard. |
| Numbers and punctuation | Gives the top row to digits and exposes common punctuation immediately, while retaining alphabetic switching. |
| Phone pad | Uses a telephone-style grid with access to dialing symbols, rather than a decimal-entry surface. |
| Social entry | Places `@` and `#` directly beside letter entry. |
| URL | Exposes period, slash, and domain entry on the main surface. |
| Web search | Gives the keyboard's submission action a prominent search-oriented treatment. |

The three account-form comparisons demonstrate a separate layout requirement: keep both the field being edited and its submission action above the keyboard. One incorrect example hides the active password field; another hides the sign-in action. The correct version leaves both available. A visible text field alone is insufficient.

Light/dark pairs change surfaces, text, and key contrast while preserving these input affordances and field/action clearances. The example text and exact key geometry are not fixed layout specifications.
