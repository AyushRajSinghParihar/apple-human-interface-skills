# macOS deletion review

The correction depends on intent, consequence, and recovery—not button color. A should remove its routine confirmation; B may retain its normal default Return action; C must stop turning inspector opening into unrelated destruction.

This review uses only `interface.md` and the installed apple-hig package. The installed root, Presentation, Menus and actions, and Patterns family instructions were read, followed by Alerts, Buttons, Modality, and Undo and redo topic procedures before their supporting guides. Official links below identify the sources represented by the local snapshot; no web verification was performed.

## Decisions and concrete behavior

| Flow | Finding from the supplied brief | Correction / retained behavior | Return and cancellation contract |
| --- | --- | --- | --- |
| A — remove one photo | Routine removal has working Undo but always interrupts with an alert. This adds unnecessary modal friction. | Remove the routine alert. The explicit removal command removes only the selected photo, with one meaningful Undo operation. Preserve a discoverable recovery path. | There is no confirmation default to invoke. Do not introduce a global Return-to-delete binding. Return follows the active control/context; explicitly activating the removal control still removes the selected photo. Undo restores that photo. |
| B — Empty Archive | The person explicitly chooses irreversible destruction, then sees `Empty Archive?`, `Cancel`, and normal default `Empty Archive`. This is the deliberate-destruction exception, not a default-button violation. | Retain confirmation, the outcome-specific labels, and the normal default `Empty Archive`. Add useful consequence text: `All items in the archive will be permanently deleted. This cannot be undone.` This copy is a proposed improvement; the brief does not establish that existing supporting text is absent. | Return in the confirmation invokes Empty Archive. Cancel is available but is not the default. Cancel, Escape, and Command-Period dismiss without changing archive contents. The destructive handler runs only after confirmation. |
| C — harmless inspector | Opening the inspector unexpectedly exposes default `Delete All`; Return destroys unrelated data. This is the highest-priority defect: the action contradicts the task and conceals unexpected loss. | Inspector opening must only inspect. Remove Delete All from the inspector-opening/default path and disconnect Return from its handler. Place any legitimate bulk-delete command in an explicit, scope-relevant action. If that command is retained, explain the exact affected data before commitment. | Opening the inspector and pressing Return must not delete anything. For any necessary warning about unexpected loss, use a destructively styled, accurately scoped action beside Cancel and choose no default so Return cannot accidentally commit. Cancel is not made the default. |

For B, place Cancel leading and Empty Archive trailing in the Mac alert row; preserve native control behavior. No special caution symbol is needed merely because this is an empty-archive operation. For C, warning styling alone does not repair the wrong task transition. A later, explicitly chosen deletion can be assessed on its own intent and reversibility rather than inheriting a blanket ban on destructive defaults.

The alert guidance says common undoable deletion generally needs no confirmation, while uncommon irreversible destruction warrants one. It expressly allows a normal default for confirmation of explicitly requested destruction, requires Cancel alongside destructive actions, says not to make Cancel default, and suggests considering no default when deliberate reading is needed. These specific qualifications govern B and C rather than flattening the general preference for nondestructive primary buttons into an absolute rule. See [Alerts: Best practices](https://developer.apple.com/design/human-interface-guidelines/alerts#Best-practices), [Alerts: Buttons](https://developer.apple.com/design/human-interface-guidelines/alerts#Buttons), [Alerts: macOS](https://developer.apple.com/design/human-interface-guidelines/alerts#macOS), and [Buttons: Role](https://developer.apple.com/design/human-interface-guidelines/buttons#Role).

For A, retain Undo/Redo at the top of Edit with Command-Z and Shift-Command-Z. Proposed operation labels are `Undo Remove Photo` and `Redo Remove Photo`; restore the correct photo and visibly reveal the restoration when needed. This recovery contract applies the [Undo and redo guidance](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo#macOS). Removing A's modal interruption and keeping C's inspector focused on inspection also follow [Modality: Best practices](https://developer.apple.com/design/human-interface-guidelines/modality#Best-practices).

## Acceptance checks and current status

**Passed — supplied-description review only:** A is explicitly described as routine and undoable. B establishes deliberate initiation, irreversibility, specific action labels, Cancel, and a normal default; its Return behavior fits the documented exception. These are brief-level findings, not verified implementation results.

**Failed — supplied-description review only:** A always interrupts an ordinary recoverable action. C makes unexpected unrelated destruction the default Return result. Both require the corrections above. No runtime failure was independently reproduced.

**Not executed — required implementation acceptance checks:**

- A: Remove one selected photo without an alert; verify no other photo changes. Undo restores the same photo and relevant state in one operation; Redo removes it again. Check a multi-edit sequence, new work after Undo, save/open history policy, and offscreen restoration. Verify Edit labels and native shortcuts. Press Return in ordinary non-removal contexts and confirm no accidental deletion.
- B: Invoke Empty Archive explicitly and verify no data changes before confirmation. Confirm exact archive scope and irreversible wording. Return in the alert empties only that archive once; Cancel, Escape, and Command-Period leave it intact. Reopening after cancellation must not commit a stale action. Check that repeated activation does not stack alerts or invoke duplicate deletion.
- C: Open the inspector and press Return immediately; all unrelated data must remain unchanged. Inspect every inspector/default-key route for deletion handlers. If a bulk-delete flow remains, verify scope-specific copy, destructive styling, visible Cancel, no default in the unexpected-loss warning, and Return without explicit action selection causing no deletion. Every supported cancellation/close path preserves data and returns to the prior context.
- Across flows: Verify actual key equivalents separately from focus-based activation, initial focus and focus restoration, accessible action names and VoiceOver navigation, enlarged/localized labels, native rendering, and usable control targets. Labels and consequences must agree. Explicit keyboard activation of a focused action must not be confused with an implicit default Return action.
